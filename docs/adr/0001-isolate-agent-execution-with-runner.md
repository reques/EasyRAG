# ADR-0001：用独立 runner 隔离 Agent 执行

## 状态

已采纳；2026-10-19 已完成本机容器级验收。

## 背景

EasyRAG 的后端持有数据库凭据、数据卷并连接内部服务。工具权限策略只能决定是否调用工具，不能限制已启动代码的文件、网络和资源访问。现有 MCP stdio 进程由后端直接启动；新增 Python 执行能力不能重复使用这条路径。

## 决策

后端只通过内部 HTTP 向独立 runner 提交固定任务类型。runner 独占 Docker socket，并用固定镜像和资源参数启动临时容器。Python 容器无网络，只接收当前用户、当前会话获准使用的附件副本；输出经后端验证后写入会话产物。MCP filesystem 和 postgres 使用固定 runner 配置，后者只连接独立数据库网络并要求只读账号。12306 MCP 经独立内部网络和域名白名单代理出网。所有执行工具先经过 `ToolRegistry` 的 `enforce` 策略；runner 故障时不回退到后端本地执行。

## 结果与代价

- 后端不持有 Docker socket，执行容器不接收后端环境变量和数据卷。
- runner 仍有 Docker 主机级控制权；公网多租户部署应放在独立主机或独立 Docker daemon。
- 容器启动增加延迟，镜像、令牌、清理和日志需要运维管理。runner 不可用时执行功能不可用。
- filesystem MCP 使用专用只读 volume，旧工作目录内容需由管理员选择性迁移。当前 MCP 配置以开关逐个迁移；未启用 runner profile 的服务仍走旧路径，严格模式可拒绝它们。

## 考虑过的方案

- **直接在后端调用 Docker**：改动较少，但需要把 Docker 控制权交给持有应用凭据的后端。
- **在后端进程内执行 Python/MCP**：没有进程和资源硬边界，线程超时不能终止执行。
- **第三方托管沙箱**：减少本地运维，但会引入外部数据流转和按量成本；当前部署以本地 Docker 为主。
