# 2026-10-18 后端无响应修复

## 原因与证据

批量导入文档时，内嵌 ingestion worker 在 API 事件循环中直接调用
`get_retriever()`。Milvus 集合的 `load()` 未设置超时；主线程一直等待集合就绪，
连 `/api/v1/health` 都无法处理。进程栈确认阻塞链为
`run_ingestion → get_retriever → MilvusRetriever.__init__ → wait_for_loading_collection`。

集合加载失败的底层原因是对象存储迁移遗漏：Milvus 元数据仍引用旧存储
`volumes/minio/a-bucket` 中的对象，当前 `rustfs-milvus` 中这些对象不存在，持续返回 404。
容器健康并不代表集合数据完整。

## 数据恢复

保留原始目录，复制旧 MinIO 数据到隔离目录，用临时 MinIO 实例读取逻辑对象。
向当前 RustFS 的 `a-bucket` 补写缺失的 16 个对象，共 374,583 字节，逐个验证 SHA-256。
未覆盖已有对象，未删除或重建集合，未清空数据库及队列。
补齐对象后，集合加载完成，后端恢复响应，积压导入任务继续执行。

迁移对象存储时必须经 S3 API 复制逻辑对象，不能直接把 MinIO 的磁盘目录当作
RustFS 的数据目录；切换前验证旧集合可加载、查询，并保留原存储备份。

## 代码防护

- ingestion、重新索引和知识库检索/删除路径在后台线程初始化并访问同步向量库。
- 图谱构建的同步集合加载和扫描同样转到后台线程，加载失败直接报告任务失败。
- `MILVUS_INIT_TIMEOUT` 默认 30 秒，可设置 1–300 秒；连接、集合元数据、索引创建、
  集合加载均显式传入超时，避免无限等待。
- retriever 单例初始化加锁，防止多个导入任务并发创建集合连接；失败实例不缓存，允许重试。

回归用例覆盖慢初始化期间事件循环可响应、超时后导入状态落为失败、并发单例、
失败重试，以及 Milvus 初始化调用的超时参数。根目录 tests 继续仅在本地使用。

## 验证

- ingestion、检索隔离/API、图谱构建相关测试共 42 项通过。
- 新镜像实连 Milvus：集合成功加载并可查询，约 0.39 秒。
- 不可达 Milvus 的连接测试在约 1.37 秒内失败（配置超时为 1 秒）。
- 后端镜像已重新构建并重启；容器健康，登录、会话、工作区和 MCP 概览接口返回 200。
- 恢复后导入继续推进。另有一个文件因 Ollama 嵌入接口返回 500 而失败，
  该失败与本次 API 主线程阻塞不同，应在嵌入服务正常时重试。
